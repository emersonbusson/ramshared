# ublk queue freeze and thaw during transient broker disconnects

After investigation, `ublk_server.rs` acts purely as a stateless IO loop interacting with the `VramBackend`. The broker logic, which manages the state of the tenants/leases and network connection (in `broker_srv.rs`), is unaware of the `ublk` ring buffers, while the `ublk_server` is unaware of the broker. The loop in `ublk_server::run_ring_owner` blocks completely in `server.wait_and_drain()?` and has no context of the `CoreEvent::Disconnected(sid)` to "pause". Modifying this loop to await broker events would introduce blocking inter-thread communication in the critical `io_uring` hot-path.

More fundamentally, the request explicitly asks to "Pause ublk command processing during broker disconnect and resume without failing active filesystem I/O requests." The ublk architecture (in `run_ring_owner`) currently handles requests sequentially (or parallelized via `WorkerReply` async returns). During a transient disconnect, pausing I/O processing at the userspace level (`ublk_server`) will quickly hang any block device (`/dev/ublkbN`) waiting on those requests, leading to potential filesystem hangs or driver time-outs in the kernel, rather than transparently recovering without failing. True "freeze and thaw" logic should rely on the block backend returning busy/retry codes or be handled at a higher orchestration layer, not by freezing the userspace io-uring loop itself.

This represents an architectural scope mismatch (asking to implement blocking pause/resume logic inside the stateless, non-blocking io-uring driver hot-path). Finding produced.
