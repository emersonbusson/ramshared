# AUDIT-2.5 — Protected beta release promotion and publication

## Findings

| Sev | SPEC § | Issue | Required fix |
| --- | --- | --- |
| High | DT-1 | A reusable child can be independently triggered as well as called by `ci-contract.yml`, producing duplicate direct/reusable execution outside the same-run aggregate model. | Add a named manufactured topology refusal that detects direct trigger plus reusable caller. |
| High | DT-2 | Release Please can currently fall back to a repository or personal token, so tag producer identity is not fixed. | Require App credentials/token unconditionally and reject every fallback expression in static contract tests. |
| High | DT-2a | `prerelease: false`/`draft: false` cannot reach the intended beta-draft lifecycle, and an unsupported version override would make the target only nominal. | Verify the upstream schema/source, use its accepted deprecated `release-as` semantic version field with prerelease/draft/forced-tag settings, and parse those exact values in source tests. |
| High | DT-4/DT-5 | Tag integrity alone is not explicit publication, and independently scheduled `workflow_run` is a race-prone handoff. | Keep integrity read-only; use a protected manual dispatch with exact tag/SHA/run-ID and no `workflow_run`. |
| High | DT-5/DT-6 | A broad upload/overwrite could turn a stale or changed candidate into a false public beta. | Bind exact four files; validate remote inventory; never glob, delete, or clobber. |
| Medium | DT-5 | GitHub release `target_commitish` may remain a branch name, so treating it as the immutable release SHA would reject a valid exact tag. | Bind source via Git tag resolution, integrity-run `head_sha`, and manifest/dispatch SHA instead; test a branch-valued API response and a wrong tag/SHA refusal. |
| High | DT-2/DT-4 | The repository's selected Actions allowlist excludes `actions/create-github-app-token@*`, so App-only producer/publication would be blocked even with correct secrets. | Keep source fail-closed; declare production release NO-GO until a separately approved repository administrator allows the pinned GitHub-owned action. Do not add a weaker token fallback. |
| Medium | DT-3 | A generic `v*` path could act on historical `v0.8.0` or a later unreviewed tag. | Pin one beta target policy for `v0.9.0-beta.1`; a subsequent target requires an explicit revision. |

## Open questions

1. The repository’s GitHub App installation permissions and protected
   environment reviewers are remote state. Source checks can require their
   shape but cannot prove they are currently configured.
2. The eventual release notes/draft metadata generated by Release Please are
   outside this asset-set contract. Publication must still refuse a non-beta or
   unexpected remote release state.
3. A live proof requires an approved protected dispatch and is deliberately
   not run in this task.
4. The protected-release environment has reviewer/protected-branch controls,
   but a remote selected-action allowlist currently excludes
   `actions/create-github-app-token@*`. The App secrets are also absent. Both
   are external blockers for actual tag production/publication.

## Verdict

**GO for source-only implementation with the following hard boundaries:**

- Tests must demonstrate RED before production checker/workflow changes.
- The candidate may contain exactly archive, detached checksum, SBOM, and
  manifest; the internal archive inventory is not uploadable on its own.
- No direct workflow trigger is permitted on `ci.yml`.
- No App-token fallback, workflow-run loop, broad asset glob, overwrite, or
  automatic publication is permitted.
- `v0.8.0` remains historical and `v0.9.0-beta.1` remains a target policy,
  not a tag or publication performed by this task.
- Do not create `IMPL.md` until protected before → action → after evidence
  exists and a human has explicitly authorized the external publication.

## Closure evidence (2026-08-14)

The external blockers recorded above were closed after source implementation.
The selected-action policy and App secrets were configured without exposing
secret material; the App-authored protected run `31793790581` published release
ID `370457260` and ended in the idempotent state. Public download and all four
SHA-256 values were independently verified as `EVD-0010` in `validation.md`.
The deprecated `release-as` and exact `last-release-sha` were one-shot recovery
controls; both are removed in the post-publication configuration and the
contract now admits only the published manifest state.

## Re-audit trigger

Re-open this audit if the target tag changes, a stable channel is added,
publication needs a fifth public asset, the GitHub App permission model changes,
or the workflow is proposed to act on a host, lab, driver, daemon, or remote
state without explicit approval.
