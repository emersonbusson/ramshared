# Release integrity

> Checked-in release-validation contract. This document is governed by
> [`ci-trust-and-release-integrity`](../specs/no-milestone/ci-trust-and-release-integrity/SPEC.md).
> Its workflow source is locally validated, but this does not claim a hosted
> tag run, trusted Windows signing, release publication, or public driver
> distribution.

## Purpose

A release version and changelog describe history; they do not independently
prove which source, lockfile, toolchain, binary, package, SBOM, or signing
classification produced the published asset. RamShared release integrity binds
those facts into one validated manifest.

The release gate is separate from pull-request CI and separate from a protected
lab. It must never turn a test-signed or otherwise untrusted Windows driver
into a public normal-install asset.

## Planned release input binding

Every eligible release manifest records:

| Field group | Required fields |
| --- | --- |
| source | version tag, full commit SHA, clean-tree assertion, repository revision |
| dependency identity | `Cargo.lock` SHA-256 and pinned build/security/SBOM tool versions |
| Linux bundle | command identity, bundle file inventory, byte sizes, SHA-256 checksums, checksum verification result |
| SBOM | CycloneDX format/version, generator identity, SBOM SHA-256, source/lock binding |
| artifacts | class, public eligibility, retention or immutable release attachment, SHA-256 inventory |
| Windows driver policy | component status, signing classification, trusted-signing/attestation evidence, public eligibility |
| decision | terminal verdict, rollback trigger, sanitizer result, gaps, and next proof |

The manifest is generated from exact pinned tooling and validated before asset
publication. It contains no private key, signing password, personal identity,
private path, raw kernel address, or secret value.

## Asset eligibility

| Asset class | Eligibility rule |
| --- | --- |
| Linux bundle | Eligible only when source/lock/toolchain/bundle/SBOM hashes validate and the protected release aggregate passes. |
| Source archive | Eligible only when tied to the same validated tag and source SHA. |
| Windows user-space diagnostic material | Eligible only when sanitized and classified; it is not driver trust evidence. |
| Windows driver with test signing | Always rejected from public promotion. It may remain isolated-lab evidence only. |
| Windows driver with unknown or untrusted signing | Rejected from public promotion. |
| Windows driver with verified production trust | Requires a separately recorded signing/attestation proof and all product-specific release gates. |
| Raw lab dump or private evidence | Never a release asset. |

An absent or environment-bound Windows trust chain is an explicit `PARTIAL`
condition. It must not block an otherwise valid Linux release from being
described accurately, but it must block a public Windows driver claim.

## Planned release flow

1. A protected release path receives a trusted tag/revision only.
2. It checks source/tag binding, clean-tree state, and lockfile identity.
3. It builds the Linux bundle with the documented release command and verifies
   every generated checksum.
4. It generates a CycloneDX SBOM using an exact pinned generator and records
   its hash.
5. It writes and validates the release manifest.
6. It rejects any public-ineligible artifact, especially a test-signed Windows
   driver.
7. It attaches only verified release evidence and publishes only after the
   final aggregate succeeds.

No pull-request workflow receives release authority, signing authority, or a
release environment secret.

## Required refusal cases

The future release validator must reject, with a non-zero result and sanitized
diagnostic, each of these cases:

- tag does not bind to the declared full source revision;
- source tree is dirty or lockfile hash differs;
- bundle inventory, byte size, or SHA-256 differs from the manifest;
- SBOM is missing, malformed, generated by an unpinned tool, or hash-mismatched;
- artifact has no retention/attachment classification or failed sanitization;
- a Windows driver is marked test-signed, unknown, untrusted, or unattested
  while requested for public promotion; and
- remote release/signing authority evidence is absent.

The last condition is environment-bound. It causes `PARTIAL` rather than a
fabricated trusted-signing result.

## Artifact handling

Release evidence is attached as immutable release material after validation.
Temporary workflow diagnostics are not the durable release record and retain
only according to the CI artifact policy. Hashes in the release manifest make
the durable evidence independently auditable after temporary artifacts expire.

## Rollback

Rollback is selected before publication. The release manifest names the prior
known-good release and the observable trigger that selects it. A release is
halted or rolled back if any manifest binding fails, one published checksum
differs, an SBOM cannot be verified, an ineligible Windows driver is selected,
or sanitizer output contains prohibited data.

No release workflow may compensate for a signing, driver, or platform gap by
changing product state, silently omitting the condition, or publishing a
test-signed substitute.
